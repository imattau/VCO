# vco-social Delta Sync — Design Spec

**Date:** 2026-03-15
**Status:** Approved
**Scope:** `packages/vco-social` (Rust backend + TypeScript frontend)
**Approach:** Hybrid — Rust owns the libp2p stream; TypeScript runs the bisect loop over IPC

---

## Overview

The relay delta-sync test (`packages/vco-relay/test/delta-sync.test.ts`) defines and proves the `/vco/sync/3.2.0` protocol contract. `vco-social` currently has none of the client-side machinery to participate in that protocol. This spec closes all 10 identified gaps, enabling the mobile app to connect to a VCO relay and receive only the envelopes it is missing — without re-downloading the full set.

---

## Gap Inventory

Ten gaps were identified by analysing `vco_node.rs`, `lib.rs`, `NodeClient.ts`, and `VcoStore.ts` against the delta-sync test contract. Each gap is marked with the design section that closes it.

| # | Severity | Gap | Closed by |
|---|---|---|---|
| 1 | Critical | `VcoBehaviour` has no `/vco/sync/3.2.0` stream protocol handler | Section 1 |
| 2 | Critical | No Negentropy/range-proof bisect client logic in Rust | Section 1 (delegated to TS via IPC) |
| 3 | Critical | No `SyncWithRelay` variant in `NodeCommand` enum | Section 1 |
| 4 | Critical | No `sync_with_relay` Tauri command in `lib.rs` | Section 2 |
| 5 | Critical | No `syncWithRelay()` on `NodeClient` | Section 3 |
| 6 | High | No distinct IPC event for delta-synced envelopes | Section 2 |
| 7 | High | `NodeClient.handleEvent` never writes envelopes to `VcoStore` | Section 3 |
| 8 | High | `syncStatus` field on `StoredEnvelope` exists but is never set | Section 3 |
| 9 | High | Rust has no access to local envelope fingerprint set for bisect | Section 3 (`getAllHeaderHashes`) |
| 10 | High | No sync trigger or UX affordance in the app | Section 4 |

## Section 1: Rust Changes

### 1a. New `libp2p-stream` behaviour

Add `libp2p-stream` to `Cargo.toml` for `vco-social`. This is the canonical upstream crate for opening ad-hoc protocol streams in libp2p-rust; no ADR is required.

Add a `stream: libp2p_stream::Behaviour` field to `VcoBehaviour` on both mobile and desktop build paths. The behaviour carries no platform-specific configuration.

### 1b. Session state

Each sync session is identified by a `session_id: String` generated by the TypeScript caller (via `crypto.randomUUID()`).

`VcoNodeState` gains a second field alongside `swarm_tx`:

```rust
pub struct VcoNodeState {
    pub swarm_tx: Mutex<Option<mpsc::UnboundedSender<NodeCommand>>>,
    pub sync_sessions: Mutex<HashMap<String, mpsc::UnboundedSender<Vec<u8>>>>,
}
```

The swarm task writes a session's write-sender into `sync_sessions` when a session is created, and removes it on session close or error. The `sync_respond` Tauri command looks up the sender here via `State<'_, VcoNodeState>` — this is the only path from Tauri commands to the per-session write channel.

The `session_id` is included on every IPC event emitted toward the frontend and on every `sync_respond` invoke call from the frontend, preventing frame mixing across concurrent sessions.

### 1c. New `NodeCommand` variant

```rust
SyncWithRelay { relay_addr: String, session_id: String }
```

`relay_addr` is the full multiaddr of the relay (e.g. `/ip4/1.2.3.4/tcp/9000/p2p/12D3...`). `session_id` is generated by the TypeScript caller.

### 1d. `libp2p_stream::Control` acquisition

`libp2p_stream::Behaviour` exposes a `Control` handle via `behaviour.new_control()`. This must be called **before** the swarm event loop begins — i.e. immediately after swarm construction in `start_node`, before the `tokio::spawn` closure. The `Control` is moved into the spawn closure and held for the lifetime of the event loop. When `NodeCommand::SyncWithRelay` is received, `control.open_stream(peer_id, StreamProtocol::new("/vco/sync/3.2.0"))` is called to open the stream.

### 1e. Stream open sequence

When the swarm task receives `NodeCommand::SyncWithRelay`:

1. Parse `relay_addr` to extract the `PeerId` from the `/p2p/...` component.
2. Dial the relay addr if not already connected; await `ConnectionEstablished` for that peer before proceeding (with a timeout).
3. Call `control.open_stream(peer_id, StreamProtocol::new("/vco/sync/3.2.0"))`.
4. Create an `mpsc::unbounded_channel::<Vec<u8>>()` for the write half.
5. Insert the write-sender into `state.sync_sessions` under `session_id`.
6. Emit `NodeEvent::SyncSessionReady { session_id }` — this is the signal for the TypeScript bisect loop to begin.

### 1f. Frame forwarding loop

After emitting `SyncSessionReady`, Rust spawns a task that:

- **Read half**: reads length-prefixed frames from the relay stream (4-byte big-endian length prefix, matching `packages/vco-transport/src/frame.ts`). Each complete frame is base64-encoded and emitted as `NodeEvent::SyncFrame { session_id, frame_b64 }`. When a zero-length frame is received, it is forwarded as a `SyncFrame` with empty `frame_b64`, then `NodeEvent::SyncComplete { session_id, received_count }` is emitted, and the session's write-sender is removed from `state.sync_sessions`.
- **Write half**: drains the `write_rx` channel, writing each `Vec<u8>` to the stream's write half.

On any IO error, `NodeEvent::SyncError { session_id, message }` is emitted and the session entry is removed from `state.sync_sessions`.

## Section 2: IPC Protocol

### 2a. New `NodeEvent` variants (Rust → TS)

Added to the `NodeEvent` enum in `vco_node.rs` and mirrored in the `NodeEvent` union type in `NodeClient.ts`:

```rust
SyncSessionReady { session_id: String },
SyncFrame        { session_id: String, frame_b64: String },
SyncComplete     { session_id: String, received_count: u32 },
SyncError        { session_id: String, message: String },
```

Serialised with `#[serde(rename_all = "camelCase")]` to match the existing event convention. The `type` discriminant values are `sync_session_ready`, `sync_frame`, `sync_complete`, `sync_error` (matching `#[serde(tag = "type", rename_all = "snake_case")]` already on the enum).

| Event | Direction | Purpose |
|---|---|---|
| `sync_session_ready` | Rust → TS | Stream open; bisect loop may begin |
| `sync_frame` | Rust → TS | One complete length-prefixed frame from relay |
| `sync_complete` | Rust → TS | Zero-length sentinel forwarded; pull phase done |
| `sync_error` | Rust → TS | Stream/dial error; session aborted |

### 2b. New Tauri commands (TS → Rust)

```
sync_with_relay(relay_addr: String, session_id: String) -> Result<(), String>
sync_respond(session_id: String, frame_b64: String)     -> Result<(), String>
```

Both defined in `lib.rs` and registered in `invoke_handler!`.

- `sync_with_relay` — sends `NodeCommand::SyncWithRelay` to the swarm channel via `state.swarm_tx`; returns immediately (fire-and-forget into the channel). The actual dial and stream open happen asynchronously in the swarm task.
- `sync_respond` — decodes `frame_b64` from base64, looks up the write-sender in `state.sync_sessions` by `session_id`, and sends the bytes. Returns `Err("session not found")` if the session is unknown or already closed. TS callers should log this error but need not abort — it indicates a race with session teardown.

### 2c. Wire framing

The relay uses 4-byte big-endian length-prefix framing (defined in `packages/vco-transport/src/frame.ts`). Rust reads one complete frame per `SyncFrame` emission. The TypeScript side always receives one complete protocol message per event — no partial-read reassembly is needed in TS.

## Section 3: TypeScript Changes

### 3a. `NodeEvent` union additions (`NodeClient.ts`)

```typescript
| { type: 'sync_session_ready'; sessionId: string }
| { type: 'sync_frame';         sessionId: string; frameB64: string }
| { type: 'sync_complete';      sessionId: string; receivedCount: number }
| { type: 'sync_error';         sessionId: string; message: string }
```

### 3b. New public fields on `NodeClient`

```typescript
public syncInProgress: boolean = false;
public lastSyncAt: Date | null = null;
public relayAddr: string | null = null;  // loaded from localStorage key 'vco.relay_addr'
```

### 3c. `NodeClient.syncWithRelay(relayAddr: string): Promise<void>`

Public method. Steps:

1. Guard: if `syncInProgress`, return immediately.
2. Set `syncInProgress = true`.
3. Generate `sessionId = crypto.randomUUID()`.
4. Invoke `sync_with_relay` Tauri command with `relayAddr` and `sessionId`.
5. Await `sync_session_ready` for this `sessionId` via a filtered event promise, with a 10 s timeout (on timeout: set `syncInProgress = false`, emit local `sync_error`).
6. Call `this._runBisectLoop(sessionId)`.
7. On `sync_complete` or `sync_error`: set `syncInProgress = false`, set `lastSyncAt` on success, notify listeners.

### 3d. `NodeClient._runBisectLoop(sessionId: string): Promise<void>`

Private method. Direct port of `runClientDeltaSync` from the delta-sync test, with these substitutions:

| Test construct | `_runBisectLoop` substitute |
|---|---|
| `channel.receive()` | Dequeue from per-session `AsyncQueue<Uint8Array>` fed by `sync_frame` events |
| `channel.send(bytes)` | `invoke('sync_respond', { sessionId, frameB64: base64(bytes) })` |
| `localStore` Map | `VcoStore.getAllHeaderHashes()` called once before the first `sendRangeProofs` |
| Received envelope write | `VcoStore.storeEnvelope(env, 'synced')` + synthetic `envelope` event |

`AsyncQueue<T>` is a small private helper (a `Promise` chain backed by a queue array and a pending-resolve slot) defined in `NodeClient.ts`. It allows the sequential bisect loop to `await` frames that arrive asynchronously as IPC events.

Imports added: `SyncRangeProofProtocol`, `computeRangeFingerprint` from `@vco/vco-sync`; `decodeEnvelopeProto` from `@vco/vco-core`. Both are existing workspace dependencies. (`encodeEnvelopeProto` is not imported — the push phase is out of scope.)

### 3e. `VcoStore` new methods

**`getAllHeaderHashes(): Promise<Uint8Array[]>`**

Opens a readonly transaction on `envelopes`, iterates all records via `getAll()`, hex-decodes the `headerHash` string field of each `StoredEnvelope`, and returns the resulting `Uint8Array[]`. `computeRangeFingerprint` (from `@vco/vco-sync`) accepts `Uint8Array[]` — the hex-to-bytes conversion happens inside this method so callers receive the correct type. Requires adding `headerHash: string` (hex) to `StoredEnvelope` and populating it on write (see 3f).

**`storeEnvelope(env: VcoEnvelope, syncStatus: 'pending' | 'synced'): Promise<void>`**

Single write path for all envelope storage. Builds a `StoredEnvelope` from a decoded `VcoEnvelope`, setting `syncStatus` as given, and calls `putEnvelope`. Replaces any ad-hoc direct calls to `putEnvelope` elsewhere in the codebase.

### 3f. `StoredEnvelope` schema addition

Add `headerHash: string` (hex-encoded `env.headerHash`) to the `StoredEnvelope` interface and to all writes. This field is what `getAllHeaderHashes()` reads back. No IndexedDB schema version bump is required — the field is stored inline on the existing object store record.

### 3g. Gossipsub envelope writes (gap #7)

In `NodeClient.handleEvent`, the existing `envelope` branch (currently only forwarding to listeners) is extended to call `VcoStore.getInstance().storeEnvelope(decoded, 'pending')` after decoding the base64 proto bytes with `decodeEnvelopeProto`. Write errors are logged but do not propagate (fire-and-forget).

## Section 4: Trigger / UX

### 4a. Automatic trigger on relay connection

`NodeClient.handleEvent` is extended: when a `dial_success` event arrives and `this.relayAddr` is non-null and `event.addr` starts with `this.relayAddr` (exact prefix match against the stored relay multiaddr), `syncWithRelay(this.relayAddr)` is called automatically. Matching against the stored `relayAddr` rather than a generic `/p2p/` substring check prevents spurious sync attempts on every peer connection. This covers the primary mobile use-case: app opens, dials the configured relay, sync happens without user action.

### 4b. Manual trigger in `SettingsView`

A "Sync now" button is added to `SettingsView`. It is:

- Visible only when `NodeClient.isReady` is true and `NodeClient.relayAddr` is non-null.
- Disabled (with a spinner) while `NodeClient.syncInProgress` is true.
- A status line below shows `lastSyncAt` as a relative time string ("Last synced 2 minutes ago"), or "Never synced" if null.

Tapping the button calls `NodeClient.getInstance().syncWithRelay(NodeClient.getInstance().relayAddr!)`.

### 4c. Relay address configuration

`relayAddr` is loaded from `localStorage` key `vco.relay_addr` on `NodeClient` construction. A text input in `SettingsView` (already present in the UI) writes to this key on change and updates `NodeClient.getInstance().relayAddr` in memory.

### 4d. Concurrency guard

`syncWithRelay` returns immediately without starting a new session if `syncInProgress` is already true. This prevents races between the automatic trigger and a manual tap.

### 4e. Silent completion

Sync completion produces no toast or notification. Delta-synced envelopes enter the store and appear in the channel feed via the synthetic `envelope` event that `_runBisectLoop` emits for each received envelope — the same path as live gossipsub messages. A "N new messages" badge is deferred to a future iteration.

## Data Flow Diagram

```
TS: syncWithRelay(addr)
  │  invoke sync_with_relay(addr, sessionId)
  ▼
Rust: NodeCommand::SyncWithRelay
  │  dial relay, open /vco/sync/3.2.0 stream
  │  emit sync_session_ready
  ▼
TS: _runBisectLoop(sessionId)
  │  getAllHeaderHashes() → localHashes
  │  SyncRangeProofProtocol.sendRangeProofs(initialProofs)
  │    invoke sync_respond(sessionId, frameB64)
  │      ▼
  │    Rust: write frame to stream
  │
  │  ← relay sends range proof response frames ←
  │    Rust reads frame, emit sync_frame(sessionId, frameB64)
  │      ▼
  │    TS AsyncQueue.enqueue(bytes)
  │  SyncRangeProofProtocol.receiveRangeProofs()
  │    ← dequeue from AsyncQueue
  │  [bisect rounds repeat until convergence]
  │
  │  ← relay streams missing envelope bytes ←
  │    Rust emit sync_frame per envelope
  │    Rust emit sync_frame('') for zero-length sentinel
  │      ▼
  │    TS: decodeEnvelopeProto(bytes)
  │    VcoStore.storeEnvelope(env, 'synced')
  │    emit synthetic 'envelope' event → UI updates
  ▼
Rust: emit sync_complete(sessionId, receivedCount)
TS: syncInProgress = false, lastSyncAt = now
```

## Out of Scope

- Push phase (client uploading its envelopes to the relay after pull) — the relay already handles this via the existing push path; the client does not need to implement it for the pull to work.
- PoW admission on synced envelopes — validation of incoming delta-sync envelopes against PoW policy is deferred.
- "N new messages" badge or notification on sync completion.
- Automatic periodic re-sync (e.g. every N minutes in background).
- Multiple concurrent relay connections.
